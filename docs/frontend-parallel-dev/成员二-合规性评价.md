# 成员二：合规性评价模块开发约定

本文约定**成员二**在并行开发中的职责边界、代码与资源放置位置，以及 Git 合并与自测要求。全组通用规则见同目录 [README.md](./README.md)。

---

## 1. 负责范围与路由

| 项目 | 说明 |
|------|------|
| **路由 path** | `/compliance` |
| **页面入口** | `frontend/src/pages/compliance/index.tsx` |
| **侧栏菜单** | 「合规性评价」，配置在 `frontend/src/routes/menu.tsx` |

**职责概要**：合规性评价全流程的前端承载，包括（随产品拆分）规则与预设、企标上传与解析进度、专用表编辑、多轮人工审核、指标比对与映射确认、报告/证书入口等。需求文档中强调**长流程、人机协作、留痕**，前端侧需预留**步骤状态**与**异步任务反馈**（轮询或后续 WebSocket），**不实现**后端算法与存储逻辑。

若未来在单模块下增加子路由（例如 `/compliance/tasks/:id`），在 `routes/index.tsx` 的 `compliance` 下增加 `children`，并与成员五、成员一协调导航入口，避免重复造路由。

---

## 2. 代码目录与文件命名

以 `frontend/src/pages/compliance/` 为业务根目录：

| 类型 | 放置位置 | 说明 |
|------|----------|------|
| 页面入口 | `pages/compliance/index.tsx` | 可为工作台总览；复杂时可拆子路由组件到 `pages/compliance/routes.tsx` 或各子目录 |
| 步骤/子页面组件 | `pages/compliance/components/` | 如 `SpecialTableEditor.tsx`、`MetricComparePanel.tsx` |
| 流程与表单 | `pages/compliance/components/` + ProForm/Steps | 多步表单单模块内聚 |
| hooks | `pages/compliance/hooks/` | 如 `useComplianceTask.ts`、`usePollingJob.ts` |
| 工具 | `pages/compliance/utils/` | 比对展示、单位换算展示等纯前端逻辑 |
| 静态资源 | `pages/compliance/assets/` | 示意图、模块专用图标 |
| 接口 | `frontend/src/services/compliance.ts` | 任务创建、状态查询、专用表保存等；体积过大时改为 `services/compliance/` 目录按子域拆文件 |
| 状态 | `frontend/src/stores/compliance.ts` | 当前任务 ID、步骤索引、草稿等（注意持久化策略与需求「断点恢复」对齐后端契约） |
| 类型 | `frontend/src/types/compliance.ts` | 专用表 JSON、比对结果、与后端统一的 DTO |

跨模块复用组件（如通用 PDF 阅读器壳、通用 Diff 视图）放在 `frontend/src/components/`，命名带业务中性前缀，便于成员五「系统审计」等模块复用。

## 3. Ant Design / ProComponents 使用边界

- **表格与表单**：密集表格、可编辑表优先 **ProTable / EditableProTable、ProForm**，减少重复封装。
- **长任务**：解析、比对等耗时操作须配合 **进度/轮询 UI**（Progress、Steps 状态），禁止长时间阻塞主线程；与需求文档中非功能性要求「超过 5 秒须异步」一致。
- **分屏联动**：若实现 PDF 与表格联动，将「联动协议」（页码、锚点）写在 hooks 或 `utils/`，便于后续换 PDF 实现时不改业务组件结构。

---

## 4. 接口与 Mock

- 所有请求经 `services/request.ts`，业务方法集中在 `services/compliance.ts`（或子目录）。
- 任务状态、轮询间隔与后端约定后写在统一常量或配置中，避免魔法数字散落。
- Mock：可临时在 service 层返回静态数据，文件内标注 `TODO` 与接口路径，便于联调替换。

---

## 5. Git 分支、PR 与 Code Review

- **个人分支**：在 GitHub 上以主分支为基线创建**自己的功能分支**，合规模块相关修改**全部在该分支上**完成后再发 PR 合入主分支；勿直接在主分支上开发。完整流程见 [README.md - GitHub 分支与合并流程](./README.md#github-分支与合并流程)。
- **分支命名**：`feature/compliance-<简述>`，例如 `feature/compliance-special-table`。
- **PR 粒度**：单功能或单一步骤闭环，避免一个 PR 同时改仪表盘、预警等无关模块。
- **共享文件**：仅在新增子路由、菜单项时编辑 `routes/index.tsx`、`menu.tsx`，合并前同步主分支，PR 中说明「合规模块」范围。

## 7. 与其他成员的协作点

- **企业档案 / 一企一库**：数据归属以后端为准，前端仅在接口契约上与成员五（企业档案页）对齐字段命名，避免各写各的 type。
- **报告下载**：若与「模板与存档」共用下载入口，与成员三约定统一组件或跳转路径。
