## 1. 整体架构设计哲学

本平台的技术选型遵循**“强业务后台、高效率前端、可伸缩算法层”**的原则。考虑到标准行业数据极度严谨、业务逻辑存在大量人工干预（Human-in-the-loop）且长远需要接入大模型（LLM）的特点，选型重点在**数据治理能力**与**工作流的可控性**。

- **后端技术栈**：Python 3.12 + Django Ninja + LangGraph + Celery
    
- **前端技术栈**：React 18 + Ant Design 5.0 + ProComponents
    
- **数据库技术栈**：PostgreSQL 16 + Redis
    
- **文档解析引擎**：Dify (1.0) / LangGraph (2.0) + Marker + PyMuPDF

## 2. 前端架构：React 18 + Ant Design 5.0

### 2.1 选型理由

- **Ant Design ProComponents 的降维打击**：本系统包含大量复杂的表单（规则预设）和数据密集的表格（专用表、比对清单）。AntD 的 ProTable 和 ProForm 能够通过配置化方案减少 60% 的前端业务代码。
    
- **严谨的状态管理**：React 的函数式编程和 Hooks 机制，配合 **Zustand**，在处理复杂的“合规评价工作台”时，能确保数据流向清晰，方便调试复杂的分屏联动逻辑。
    

### 2.2 技术对比

|   |   |   |
|---|---|---|
|维度|React + Ant Design|Vue 3 + Element Plus|
|**组件库深度**|**胜**。AntD ProComponents 专为 B 端设计，处理复杂报表更专业。|优。Element Plus 适合常规管理，但在极其复杂的业务报表上开发量略大。|
|**逻辑抽象**|**胜**。Hooks 机制在处理“PDF预览+表格联动”这种跨组件逻辑时更优雅。|优。组合式 API 同样出色，但生态中针对标准比对这类组件的封装较少。|
|**长远维护**|**胜**。React 生态在大型、高交互系统中具备更强的健壮性和类型检查支撑。|优。适合中小型系统快速迭代。|

## 3. 后端架构：Python 3.12 + Django Ninja

### 3.1 选型理由

- **Python 的生态优势**：标准库的 PDF 解析、技术指标的 NLP 处理、以及工作流（Diffy/LangGraph）全部都在 Python 生态下。使用 Python 实现了“算法与业务同语言”，极大降低了通信损耗。
    
- **Django Ninja 的平衡艺术**：
    
    - **继承 Django 的稳健**：自带成熟的 ORM、用户鉴权和 **Admin 后台**（超级管理员快速维护分类和元数据）。
        
    - **FastAPI 的性能**：基于 Python 类型注解（Pydantic），提供异步支持和极快的执行速度，生成的 API 文档对前端极度友好。
        

### 3.2 技术对比

|   |   |   |   |
|---|---|---|---|
|维度|Django Ninja|Django REST Framework (DRF)|FastAPI|
|**开发速度**|**快**。类型注解，自动文档。|中。配置繁琐。|快。|
|**内置管理**|**有**。自带 Admin 后台。|有。|**无**。需自研管理界面，开发成本高。|
|**执行性能**|**极高**。原生异步支持。|一般。|极高。|
|**选型结论**|**首选**。既要管理后台，又要高性能 API。|放弃。性能和语法已过时。|放弃。内部管理需求多，自研权限成本太高。|

## 4. 工作流引擎：Dify (1.0) -> LangGraph (2.0)

### 4.1 选型理由

- **1.0 阶段 (Dify)**：本项目早期需要快速验证 PDF 提取和 Prompt 效果。Dify 提供了可视化的编排，能让不熟悉代码的业务人员参与逻辑微调。
    
- **2.0 阶段 (LangGraph)**：合规性评价涉及“中断-审核-恢复”的长流程。LangGraph 的**状态机模型**和**持久化 Checkpoint** 能够完美解决人工干预时的状态丢失问题，是实现“稳定留痕”的技术核心。
    

### 4.2 技术对比

|   |   |   |
|---|---|---|
|维度|Dify|LangGraph|
|**控制力**|低。黑盒 API 调用。|**极高**。每一行 Python 逻辑均可控。|
|**人工在环**|弱。难以实现复杂的中断恢复。|**极强**。原生支持 interrupt 和任务重放。|
|**逻辑重用**|难。逻辑散落在 UI 配置中。|**易**。代码化模块，可进行单元测试。|

## 5. 数据库：PostgreSQL 16

### 5.1 选型理由

- **JSONB 处理指标多样性**：技术指标各异（数值、范围、文本），MySQL 的 JSON 支持较弱。PostgreSQL 的 JSONB 支持 GIN 索引，使得我们在查询“所有压力指标大于 50 的企标”时依然保持毫秒级响应。
    
- **谱系关联的递归查询 (CTE)**：标准替代关系（A-B-C-D）是典型的树状结构。PG 对递归查询的优化远超 MySQL，能够轻松处理几十万条标准的溯源计算。
    

### 5.2 技术对比

|   |   |   |
|---|---|---|
|维度|PostgreSQL|MySQL|
|**复杂查询**|**极强**。支持窗口函数、递归 CTE。|一般。|
|**非结构化支持**|**卓越**。JSONB 性能堪比 NoSQL。|基础。索引和操作函数有限。|
|**选型结论**|**必选**。为了标准谱系和多变指标设计。|放弃。处理树状结构和复杂 JSON 太吃力。|

## 6. 异步任务与缓存：Celery + Redis

### 6.1 选型理由

- **解耦长耗时任务**：PDF 解析和全库合规预警是重型任务。Celery 作为 Python 界的标准任务队列，能确保前端请求不被阻塞，提供稳定的异步处理能力。
    
- **Redis 的多功能性**：既作为 Celery 的消息代理（Broker），也用于缓存高频访问的标准目录，并存储工作流的临时状态。
    

## 7. 文档解析：Marker / PyMuPDF

### 7.1 选型理由

- **Marker**：目前最先进的 PDF 转 Markdown 引擎，能有效识别标准文件中的层级结构、表格和数学公式，这是实现“正文拆解（1.3）”的技术前提。
    
- **PyMuPDF**：用于实现前端 PDF 预览时的坐标精确定位。
    

## 8. 总结：架构的核心竞争力

这套技术栈的核心竞争力在于 **“逻辑的严丝合缝”**：

1. **Django Ninja** 稳住了数据管理与权限的底座；
    
2. **React + AntD Pro** 解决了海量数据展示的效率问题；
    
3. **LangGraph** 承载了最具挑战性的“有人工干预的算法流”；
    
4. **PostgreSQL** 容纳了复杂的标准体系逻辑。
